## Measured outputs vs. reproducible outputs

`gen_benchmarks` and `gen_peak_memory` produce **measurements**, not
artifacts. Their numbers are a function of the machine and the moment
the run happened, so two clean builds of the same commit will
legitimately disagree about them. Comparing the measured reports
byte-for-byte would be a check that can only ever fail.

Each generator therefore has a `--shape` mode that writes the same
report with every measured number replaced by a sentinel
(`<MEASURED>` in Markdown, `null` in JSON):

| Artifact | Contents | Reproducible? |
|---|---|---|
| `docs/benchmarks.md` / `.json` | Wall-clock durations, peak RSS, generation timestamp | No — machine-dependent by nature |
| `docs/benchmarks.shape.md` / `.json` | Benchmark ids, iteration counts, input digest, report skeleton | **Yes** — byte-identical on any host, toolchain or profile |
| `docs/peak-memory.md` / `.json` | Per-scenario `VmHWM` / `VmRSS` / `VmPeak` | No — kernel-dependent by nature |
| `docs/peak-memory.shape.md` / `.json` | Scenario ids, expectations, accept/reject outcomes, stable error codes, budgets | **Yes** — byte-identical on any host, toolchain or platform |

The shape files are what `.github/workflows/reproducible-build.yml`
compares across its two clean containers, alongside the artifact set
(the normative manifest, the binary reference vectors, the conformance
corpus and the example package). The local mirror of that check is
`crates/elang-conformance/tests/measurement_shape.rs`, which runs each
generator twice in one test invocation and asserts the outputs are
byte-identical.

The measured reports are still generated on every CI run, so the
harness is proven to work; only their *structure* is compared.

## Integrity vs. publisher authenticity

> **SHA-256 integrity does not establish publisher authenticity.**

The SHA-256 hashes recorded in
`specs/registry/normative-manifest.json`, in every fixture's
`.sha256` sidecar, in `fixtures/corpus_index.json`, and in
`docs/release/v0.1.0/reproducible-build-evidence.md` — a file the
`reproducible-build` CI workflow *writes at run time*, and which is
therefore absent from a source checkout — attest that the bytes you
have match the bytes the release process produced. They do **not** prove who produced those
bytes, that the producer is the RockyDevWorks project, or that the
producer has any claim on the `urn:elang:*` URN namespace or on any
media-type registration.

The v0.1.0 release deliberately ships **without** a publisher
authenticity claim. The branch does not:

* sign release artifacts,
* create the `v0.1.0` tag or publish anything to a registry,
* request or claim a registered media type (`application/vnd.elang.v0.1+zip`),
* claim ownership of any URN namespace beyond what the published
  conformance corpus and example packages demonstrate through their
  byte content,
* request a code-signing certificate or distribution-platform listing.

If a downstream consumer wants to verify that the package they
downloaded was produced by this repository, they must rely on an
*out-of-band* mechanism: a signed tag, a transparency log, or a
mirror they trust. The SHA-256 hashes are sufficient to detect
*modification* of the bytes; they are not sufficient to attest
*provenance*.

## Reproducing this release's outputs

```sh
# Conformance corpus (the 60 published fixtures + index + schema;
# 74 fixture directories on disk — see fixtures/CORPUS.md).
cargo run -p elang-conformance --bin gen_conformance_corpus

# Canonical ELD goldens.
cargo run -p elang-conformance --bin gen_canonical_goldens
cargo run -p elang-conformance --bin gen_epf_canonical_goldens

# Binary reference vectors (OA-11).
cargo run -p elang-conformance --bin gen_binary_vectors

# Example package.
cargo run -p elang-conformance --bin gen_example_package

# Normative manifest (pinned checksum source).
cargo run -p elang-conformance --bin gen_normative_manifest

# Performance + memory reports.
cargo run -p elang-conformance --bin gen_benchmarks
cargo run -p elang-conformance --bin gen_peak_memory

# The byte-reproducible shape variants, used by the reproducible-build
# CI workflow (see `## Measured outputs vs. reproducible outputs` below).
cargo run -p elang-conformance --bin gen_benchmarks -- --shape
cargo run -p elang-conformance --bin gen_peak_memory -- --shape

# Archival checksum metadata.
cargo run -p elang-conformance --bin gen_release_archive

# The distributable source artifact and its SHA-256 sidecar. Deterministic:
# two builds of the same tree produce the same bytes. Creates no tag,
# publishes nothing and makes no network call. Requires GNU tar, so run it
# on Linux — the release platform.
scripts/build-release-artifacts.sh --verify
```

Every generator that emits a **deterministic artifact** is
idempotent: re-running it on an unchanged tree rewrites nothing and
the working tree stays clean. A divergence is the bug; the next step
is to rebase, not to hand-edit the output.

The two exceptions are the **measured** generators, `gen_benchmarks`
and `gen_peak_memory`: their outputs embed timings, peak-memory
readings and a wall-clock timestamp, so re-running them always
changes `docs/benchmarks.{md,json}` and `docs/peak-memory.{md,json}`.
That is expected, not a divergence. The byte-reproducible side of
those two generators is their `--shape` mode, which is idempotent.
